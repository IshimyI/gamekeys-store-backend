# NOTES

## Однократная выдача (в двух словах)

`node:sqlite` работает синхронно — каждый `.run()`/`.get()` выполняется целиком,
без пауз для event loop. Обработчик `POST /api/webhooks/payment` написан так, что
от чтения заказа до записи нового статуса нет ни одного `await`. Значит, пока
Node обрабатывает один вебхук, он физически не может переключиться на другой
посередине — даже если оба пришли "одновременно". Это и есть вся защита от
гонок на уровне HTTP-хендлера, без ручных блокировок.

Дальше — отдельные проверки под каждый сценарий:

1. **event_id уникален** (`webhook_events.event_id` — PRIMARY KEY). Повторный
   вебхук с тем же event_id падает на `INSERT` — обработка не идёт дальше.
2. **Проверка статуса перед переходом.** Если по одному заказу пришло несколько
   разных event_id почти одновременно — первый переводит заказ в `delivering`,
   остальные видят уже другой статус и ничего не делают.
3. **Ключ забирается одним UPDATE**:

   ```sql
   UPDATE keys SET status = 'issued', issued_to_order_id = ?
   WHERE id = (SELECT id FROM keys WHERE status = 'available' LIMIT 1)
   ```

   `changes = 0` — ключей нет, это нормальный `out_of_stock`, не падение.

## Таймаут ≠ отказ, ретраи с бэкоффом, fallback A→B

У каждого обращения к поставщику свой `request_id` — `orderId:supplier:номерПопытки`.
Контракт поставщика требует: на повтор с тем же request_id вернуть тот же код,
а не выдать новый. Отсюда два разных случая:

- **Таймаут** — не значит "не получилось". Поставщик мог успеть выдать код, просто
  ответ не дошёл вовремя. В этом случае request_id не меняется: HTTP-запрос
  отвечает клиенту `timeout`, а сам вызов поставщика продолжает висеть в фоне.
  Если он всё же ответит успехом — заказ доставится этим поздним ответом, без
  повторного обращения и без второго ключа.
- **Явная ошибка (4xx/5xx)** — это законный повод попробовать снова. Тут уже
  можно взять новый request_id и повторить с бэкоффом (по умолчанию 2 попытки,
  задержка удваивается: 200мс, 400мс...). Если ошибка `out_of_stock` — повторять
  тот же поставщик бессмысленно, сразу falls back на второго. Если и после
  ретраев поставщик A не смог — идём к поставщику B по той же схеме. Если и он
  не смог — заказ уходит в `out_of_stock`/`delivery_failed` (восстановимое
  состояние, не падение).

## Сверка и денежный леджер

`ledger_entries` — append-only таблица: одна запись на заказ, `order_id UNIQUE`,
пишется в момент перехода `created → delivering` (то есть "деньги подтверждены
платёжкой"). Пишется из одной общей функции (`markPaidAndDelivering`), через
которую проходят и реальный вебхук, и тестовый форс-эндпоинт — поэтому леджер
всегда синхронен с заказами, а не только в "боевом" пути.

`GET /api/admin/reconciliation` сверяет две вещи, которые обе обязаны быть
пустыми в здоровой системе:

- `delivered_without_charge` — доставлен, но не было записи о списании,
- `charged_without_order` — есть списание без соответствующего заказа.

Плюс отдельно отдаёт `paid_but_not_delivered` — те же данные, что и
`/api/admin/undelivered-orders`, но с точки зрения денег, а не только статуса.

## Фоновое восстановление зависших заказов

`sweepStuckOrders()` по таймеру (по умолчанию раз в 15с) берёт заказы в
`out_of_stock`/`delivery_failed`, которые не трогали дольше `SWEEP_MIN_AGE_MS`
(10с), и прогоняет их через ту же функцию `runDelivery`, что и ручной retry.
Это тот же атомарный переход `recoverable → delivering`, что и у admin-эндпоинта
— гонка между sweep-тиком и ручным retry невозможна по той же причине, что и
у вебхуков (синхронность). Батчами по 5 с небольшой паузой между заказами,
чтобы не долбить поставщика пачкой запросов разом.

## Каталог под нагрузкой (design note, без реализации на тысячах SKU)

Задача не про то, чтобы накидать тестовых данных, а про то, какие решения не
дадут запросу деградировать при росте каталога:

- **Остатки не считать на лету.** Текущий пул ключей общий (не привязан к SKU)
  — это ok для демо на 12 товарах, но при реальном масштабе на каждый SKU нужен
  свой пул, и "сколько осталось" должно быть **денормализованным счётчиком**
  (`products.available_count`), который двигается тем же атомарным `UPDATE`,
  что и выдача ключа, а не считается `COUNT(*)` по `keys` при каждом открытии
  витрины.
- **Индекс под выдачу.** Если ключи привязаны к SKU — `keys(sku, status)`
  составным (или частичный `WHERE status = 'available'` в Postgres) — иначе
  запрос "найти свободный ключ для этого SKU" на больших объёмах уходит в
  скан таблицы.
- **Пагинация витрины — keyset, не OFFSET.** `WHERE sku > ? ORDER BY sku LIMIT N`
  вместо `OFFSET N LIMIT N` — иначе с ростом номера страницы запрос линейно
  замедляется, это классическая ловушка на тысячах+ строк.
- **Проверка через план выполнения.** `EXPLAIN QUERY PLAN` (SQLite) /
  `EXPLAIN ANALYZE` (Postgres) на горячий запрос витрины — цель увидеть
  `SEARCH ... USING INDEX`, а не `SCAN`. Если это Postgres — индекс `(type)`
  под фильтры категорий уже есть в схеме, для полнотекстового поиска по
  названию добавил бы `GIN`/`pg_trgm`.
- **Кэш перед горячим запросом**, если он read-heavy и не требует полной
  realtime-точности (для самой витрины устаревание на пару секунд не страшно;
  строгая атомарность нужна только в момент реальной покупки).

## Как масштабировали бы под нагрузку в целом

Сейчас вся защита от гонок держится на том, что это **один процесс** с
синхронным SQLite — Node физически не даёт двум запросам выполниться
"одновременно" внутри критической секции. Это специально: просто, дёшево,
корректно для теста. Но это же и потолок — так не масштабируется
горизонтально, больше одного инстанса на файл BD не запустишь без риска.

Что бы поменял для роста нагрузки:

1. **Postgres вместо SQLite-файла**, с той же идеей идемпотентности (UNIQUE на
   event_id/request_id никуда не денется), но атомарность через
   `SELECT ... FOR UPDATE SKIP LOCKED` при выдаче ключа и `UPDATE ... WHERE
   status = 'created'` для перехода статуса — вместо однопоточности JS.
2. **Несколько инстансов бэкенда за балансировщиком** — раз атомарность теперь
   на уровне БД, а не процесса, это становится безопасным.
3. **Фоновую задачу — в очередь** (BullMQ/Redis или аналог) вместо `setInterval`
   в каждом инстансе: иначе с двумя инстансами оба начнут одновременно мести
   одни и те же зависшие заказы. Очередь с `SKIP LOCKED`/уникальным job id
   решает то же самое, что сейчас решает синхронность.
4. **Вызовы к поставщику — тоже в очередь**, чтобы медленный/подвисший
   поставщик не держал память процесса на всё время таймаута — сейчас это
   не критично при паре сотен заказов, но на масштабе лучше отделить приём
   вебхука от долгой работы полностью.
5. **Кэш и денормализация для каталога** — см. раздел выше.

## Что упростил осознанно

- Хранилище — файл SQLite, не Postgres: для одного процесса и задачи на
  корректность конкурентной логики этого достаточно, и в условии разрешено
  ("PostgreSQL или другая реляционная").
- Пул ключей общий, не по SKU — для проверки на гонки это не принципиально,
  но в разделе про каталог написал, как делать по-другому при реальном росте.
- Реальной оплаты и поставщиков нет — обе стороны эмулируются заглушками по
  контракту, включая настраиваемую долю ошибок/таймаутов.
- Логи — построчный JSON в stdout, без внешнего сборщика. Для теста этого
  достаточно, чтобы показать структуру; в проде это ушло бы в человеческий
  агрегатор (Loki/ELK) без изменений в формате.

## Что доделал бы, будь времени вдвое больше

- Настоящие тесты (Vitest + supertest) вместо отдельного load-test скрипта —
  сейчас он одновременно и демонстрация сценариев, и единственная проверка.
- Per-SKU пул ключей вместо общего, чтобы раздел про каталог был не только
  дизайн-заметкой, а реальным кодом.
- Grace-период/TTL для заказов, зависших в `created` без вебхука вообще —
  сейчас они просто висят.

## Время

~2.5 часа: ядро (заказы, вебхук, exactly-once, схема) — 50 мин, таймауты +
бэкофф + fallback A/B — 40 мин, сверка/леджер/фоновая задача — 40 мин,
load-test сценарии и отладка — 30 мин, README/NOTES — 20 мин.
